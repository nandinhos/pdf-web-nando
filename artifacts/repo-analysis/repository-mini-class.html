pdf-web-nando, por dentro

Uma suite web de manipulação de PDF reconstruída como serviço: o navegador mostra e arrasta páginas com pdf.js, mas quem corta, junta, reconhece texto e confere assinatura é um backend Java enxuto sobre Apache PDFBox. Esta mini-aula reconstrói o modelo mental do sistema a partir do código — não do README.

Repositório github.com/nandinhos/pdf-web-nando Commit b424da7 Modo safe-run (testes + Docker + E2E executados) Stack Java 21 · Spring Boot 3.3.5 · PDFBox 3.0.3 · Next.js 14 · pdf.js

1 · O problema que ele resolve

Ferramentas de PDF no estilo PDF24 (dividir, mesclar, reordenar, imagem↔PDF, OCR, verificar assinatura) sem instalar nada e sem enviar documentos a terceiros. A origem dos requisitos é incomum e está documentada em docs/PRD.md: engenharia reversa estática do PDF24 Creator, com as funcionalidades reimplementadas sobre bibliotecas próprias — nenhum binário ou código do PDF24 é redistribuído, e o GhostScript (AGPL) ficou deliberadamente de fora.

2 · Topologia real

O drift que quebrava tudo: o docker compose up do repositório recém-clonado falhava porque a imagem minio/minio não é mais publicada publicamente (Docker Hub: denied; Quay: 401). Como o código nunca usou MinIO nem Redis, a correção foi removê-los do caminho de boot — não trocar a imagem.

3 · Os fluxos que importam

Upload → ferramenta → download (síncrono)

  1. POST /files valida o tipo real por magic bytes (%PDF-), não pela extensão, grava com UUID e conta as páginas.
  2. O frontend renderiza o mesmo arquivo localmente com pdf.js — o servidor não devolve thumbnails.
  3. Dividir, mesclar e ordenar convergem para core/PageMerger: cada serviço monta uma lista ordenada de páginas e o motor importa cada uma preservando caixa e rotação.
  4. O resultado vira um artefato em disco com downloadUrl; o nome final do arquivo é escolhido pelo usuário e sanitizado no servidor.

OCR (assíncrono, com progresso)

  1. POST /ocr cria um job e retorna na hora; o trabalho roda em @Async.
  2. Cada página é renderizada em JPEG no DPI do preset de qualidade e entregue ao processo tesseract (argumentos em lista, sem shell, timeout de 5 min).
  3. Os PDFs pesquisáveis por página são mesclados; o progresso é empurrado ao navegador por SSE.
  4. Saída dupla: PDF pesquisável + TXT. Verificado de verdade nesta sessão — o texto "Pagina 1 pdf-web-nando E2E" voltou no TXT.

Assinatura é só verificação (não assina): BouncyCastle valida o CMS, a cobertura do ByteRange e a cadeia contra as raízes do sistema. LTV e lista de confiança europeia são v2 declarada — não prometa validade jurídica completa com a v1.

6 · Armadilhas conhecidas

  • Sem autenticação nem rate-limit. Ótimo localmente; não exponha o :8090 à internet assim.
  • Upload inteiro em memória (file.getBytes()) apesar do limite declarado de 500 MB — arquivos grandes são o primeiro gargalo.
  • Nada expira: uploads, artefatos e jobs nunca são apagados (o TTL do .env.example não tem código). Disco e memória crescem com o uso.
  • Instância única por desenho: jobs e emissores SSE vivem no processo; escalar horizontalmente exige a v2 (Redis/S3) que hoje é só intenção.
  • Mesclar perde bookmarks/links internos e o OCR rasteriza a página (o PDF pesquisável é imagem + texto, não o vetor original).

Para rodar:

cp .env.example .env
docker compose -f infra/docker-compose.yml --env-file .env up --build -d
# abra http://localhost:8090 no navegador

O host não precisa de Java: o backend compila e roda em container. Para mexer no frontend com hot-reload, suba só o backend pelo compose e rode pnpm dev em frontend/.
